   position = Σ(sensor_value_i × weight_i) / Σ(sensor_value_i)

where weights correspond to physical sensor position (e.g., -2, -1, 0, 1, 2 for a 5-sensor array). This continuous error feeds into a PID controller for smooth steering rather than jerky on/off corrections — this is how most competitive line-following robots achieve fast, stable tracking.

Each of these features breaks the "smooth continuous line" assumption your PID controller relies on, so each needs its own handling logic layered on top of the base algorithm.

1. Zig-Zag Section
Problem: Sharp alternating turns need fast, aggressive correction, but your normal PID gains (tuned for smooth curves) will either overshoot (oscillate hard) or lag behind (cut corners/lose line) on sharp direction reversals.

Suggestions:

Detect it first: Track how fast error is changing sign. If lastError and current error have opposite signs and both exceed a threshold within a short time window, you're likely in a zigzag — trigger a "sharp mode."
Gain-switching (gain scheduling): Use two PID gain sets — normal gains for straights/gentle curves, and a more aggressive set (higher Kp, higher Kd, lower base speed) when zigzag is detected.
Reduce base speed in zigzag mode — sharp reversals at high speed cause wheel slip and overshoot regardless of tuning.
Consider a mechanical fix too: shortening wheelbase or lowering sensor array height slightly improves turn responsiveness independent of software.
bool zigzagMode = false;
unsigned long lastSignChange = 0;

void detectZigzag(long error) {
  if ((error > 800 && lastError < -800) || (error < -800 && lastError > 800)) {
    if (millis() - lastSignChange < 400) { // rapid alternation
      zigzagMode = true;
    }
    lastSignChange = millis();
  }
  if (millis() - lastSignChange > 600) zigzagMode = false; // timeout back to normal
}

// In lineFollow():
float Kp_use = zigzagMode ? Kp_sharp : Kp;
float Kd_use = zigzagMode ? Kd_sharp : Kd;
int speed_use = zigzagMode ? baseSpeed * 0.7 : baseSpeed;
2. Circle / Loop Section
Problem: This is the hardest one. A loop typically means the line crosses itself or returns to the same junction point — your sensor array will suddenly see many sensors active at once (a T or X-junction pattern), and the controller needs to decide which way to go rather than just "follow the centroid," because the centroid calculation breaks down when the line isn't a single clean stripe under the array.

Suggestions:

Junction detection: If a high number of sensors (e.g., 8+ of 11) read "on line" simultaneously, that's not a normal line — it's an intersection/loop point. Don't trust the weighted-centroid position in this state.
Predetermined turn rule: Most competition rules for loops specify a fixed behavior (e.g., "always exit the loop by turning the same direction you entered" or "always take the left branch"). Hard-code that decision rather than trying to compute it from the sensor pattern.
Use encoders or heading (IMU/gyro) for the loop itself: Once you detect loop entry, some teams switch to dead-reckoning around the loop — drive a preset arc (distance + heading) rather than continuing to trust the line sensors, since a circular loop can present ambiguous overlapping line segments to a linear array.
Debounce: require the "many sensors active" condition to persist for a few consecutive reads before triggering loop-handling, to avoid false triggers from noise.
int countActiveSensors() {
  int count = 0;
  for (int i = 0; i < NUM_SENSORS; i++) {
    if (isOnLine(i)) count++;  // uses your normalized threshold
  }
  return count;
}

// In main loop:
if (countActiveSensors() >= 8) {
  handleJunction();  // switch to a separate, rule-based maneuver
} else {
  lineFollow();       // normal PID
}
3. Dotted / Broken Line Section
Problem: Sensors will briefly see nothing (all readings near background) during the gaps between dashes. If your controller reacts to "line lost" by stopping or searching randomly, it'll fail here.

Suggestions:

Your -1 handling in getLinePosition() already covers the basic case — continuing in the direction of lastError. For dotted lines this is usually enough, as long as gaps are short relative to robot speed.
Add a timeout-based "coast" mode: instead of instantly snapping to a hard-turn guess when the line disappears, maintain the last known steering output (not just last error direction) for a short duration — this keeps the robot moving straight-ish through a gap rather than oversteering.
Don't apply integral windup during gaps — freeze or reset the integral term while pos == -1, otherwise it accumulates error during the gap and causes a jerk when the line reappears.
Reduce speed slightly in sections with known dotted lines, if your rules allow variable speed, since dead-reckoning accuracy degrades with distance/speed.
unsigned long lineLostTime = 0;
bool wasLineLost = false;

void lineFollow() {
  int pos = getLinePosition();
  long error;

  if (pos == -1) {
    if (!wasLineLost) {
      lineLostTime = millis();
      wasLineLost = true;
    }
    error = lastError; // hold last steering direction rather than exaggerate it
    // freeze integral to prevent windup during the gap
  } else {
    wasLineLost = false;
    error = pos - 5000;
    integral += error; // only accumulate when line is actually seen
  }

  integral = constrain(integral, -10000, 10000);
  long derivative = error - lastError;
  float output = Kp * error + Ki * integral + Kd * derivative;

  int leftSpeed  = constrain(baseSpeed + output, -maxSpeed, maxSpeed);
  int rightSpeed = constrain(baseSpeed - output, -maxSpeed, maxSpeed);
  setMotors(leftSpeed, rightSpeed);
  lastError = error;
}
Overall architecture suggestion
Rather than one monolithic PID function, structure your main loop as a state machine:

NORMAL_FOLLOW → (many sensors active) → JUNCTION_HANDLING → back to NORMAL_FOLLOW
NORMAL_FOLLOW → (rapid error sign flips) → ZIGZAG_MODE → back to NORMAL_FOLLOW
NORMAL_FOLLOW → (pos == -1) → GAP_COAST → back to NORMAL_FOLLOW (or LINE_SEARCH if gap too long)
This way each special section gets its own tuned behavior instead of forcing one PID configuration to handle everything, which is usually where LFR robots fail in competitions with mixed track features.

Do you know the specific rules for the loop section (e.g., does the line cross itself, or is it a separate closed circle connected by a single point)? That changes whether you need full dead-reckoning or just a junction rule.
